# Тестовый Срез

Новая версия интерфейса: [вход по личным ссылкам, таблица и порядок проверки](SIMPLE-TEST.md). Ниже сохранены описание инфраструктуры и первоначального прогона. Для продавцов в новом интерфейсе выдавайте личные ссылки через «Магазины и сотрудники → Доступ»; вход администратора остаётся прежним.

16.09.2026 развёрнут отдельный стэк **srez-test**, ID **103** (окружение Portainer 3), ветка Git **test**, файл **compose.test.yaml**. Порт сервера **9992**, HTTPS-адрес **https://srez-test.studio313.ru/**. Владелец получает два пароля отдельным файлом `Srez_test_access.txt`, исключённым из Git.

## Изоляция

- Свои PostgreSQL `srez_test`, том, Docker-сеть, секрет приложения и пароль базы.
- Образ `srez:test` отделён от `srez:production`. Рабочий стэк не обновляется при выкладке ветки `test`.
- Два магазина: `TEST-MS` (Мильстрим) и `TEST-KK` (Культура крепкого), один учебный сотрудник.
- `test.seller` — программист в роли продавца, доступ к обоим учебным магазинам. `test.admin` — видеоконтроль с полным управлением.
- Пароли генерируются отдельно и передаются владельцу закрытым файлом. Рабочая база и её доступы не копируются.
- Баннер «Тестовая версия Среза», отдельные имена cookie; уведомления начинаются с `[ТЕСТ СРЕЗА]` и ведут на тестовый домен.
- Команды и API тестовых прогонов отключены без `SREZ_TEST_MODE=true`. При `DEBUG=false` этот флаг требует базу с именем `srez_test`.

## Развёртывание

1. Создать HTTPS-поддомен, nginx upstream `http://185.72.147.187:9992`.
2. В Portainer создать отдельный стэк из репозитория, ветка `refs/heads/test`, Compose path `compose.test.yaml`. Задать новые `SECRET_KEY`, `POSTGRES_PASSWORD`; Telegram пока выключить.
3. Проверить фактический адрес nginx в логах нового web-контейнера. Добавить его `/32` вместе с `127.0.0.1/32` в `TRUSTED_PROXY_CIDRS` тестового стэка, обновить только этот стэк.
4. Один раз выполнить в web: `python manage.py seed_test_site --output /tmp/srez-test-access.json`. Команда откажется менять непустую базу. Скачать файл доступов владельцу. Повторно при обновлениях не запускать.
5. Войти под двумя ролями, сверить магазины и протестировать «Управление → Начать тест сейчас».

Для локальной проверки `scripts/run_test_site_local.py` использует отдельную SQLite-базу и выключает внешнюю отправку. Worker запускается той же командой с `--worker`. PostgreSQL-проверки выполняются в отдельном проекте `srez-acceptance-check`.

## Telegram

Используется существующий `@srez_notify_bot`, но **отдельная группа «Срез — тест»**. Добавить туда только участников проверки и бота. `/start` не обязателен: ID определяется и по событию добавления бота. Программист один раз привязывает эту группу к тестовому стэку. Токен хранится в переменных тестового стэка; ID группы должен отличаться от рабочего чата. Чтение `bot_chat_id telegram` не потребляет события и не меняет webhook.

Перед включением проверить `getMe` и исходящий HTTPS-доступ сервера к `api.telegram.org:443`. Ранее наблюдался тайм-аут прямого соединения. Токен не отправлять публичным прокси, TLS не отключать. При необходимости использовать доверенный маршрут владельца сервера.

На 16.09 токен проверен с компьютера владельца: Telegram подтвердил `srez_notify_bot`. С сервера TCP к `149.154.166.110:443` завершается тайм-аутом; GitHub и MAX доступны. Отправка пока выключена. Для завершения нужны доступный серверу маршрут и ID тестовой группы; последнее чтение `getUpdates` вернуло пустой список, вебхук не установлен.

После выбора группы задать её `TELEGRAM_CHAT_ID`, включить `TELEGRAM_ENABLED=true` **только у srez-test**. Реальная доставка подтверждается сообщением в группе и временем последней отправки в «Управление → Уведомления».

## Совместная проверка

1. Видеоконтроль входит как `test.admin`, программист — как `test.seller`. Оба видят жёлтую отметку тестовой версии.
2. Видеоконтроль проверяет сотрудника, назначение в два магазина и планы 25 000 ₽ / 25 чеков / 35 единиц. Затем нажимает **«Начать тест сейчас»**.
3. Первый срез открыт сразу, крайний срок через 3 минуты. Второй открывается через 3 минуты, крайний срок через 6. Закрытие открывается через 6 минут, крайний срок через 9. Точные сроки отображаются в интерфейсе, по Москве.
4. Программист сдаёт Мильстрим: 5 000 ₽, 5 чеков, 8 единиц. Первую сдачу Культуры крепкого намеренно пропускает до срока.
5. Через 3 минуты и до 30 секунд на проверку worker офис должен увидеть опоздание Культуры и получить тестовое уведомление Telegram. Ссылка открывает именно её отчёт.
6. Теперь программист сдаёт Культуру: 4 000 ₽, 4 чека, 6 единиц. Это поздняя первая сдача; офис получает соответствующее уведомление.
7. Видеоконтроль задаёт вопрос из карточки Мильстрима, программист отвечает через «Ответ видеоконтролю». Ответ появляется в карточке и уведомлении. Сам вопрос офиса отдельного сообщения в офисную группу не создаёт.
8. Для второго среза Мильстрима ввести намеренно меньшую выручку 3 000 ₽ при 6 чеках и 9 единицах, с пояснением «Учебная ошибка». Офис видит замечание. Затем исправить на 12 000 ₽ / 12 / 18 с причиной «Исправление учебной ошибки». Проверить историю двух версий. Второй срез Культуры: 9 000 ₽ / 9 / 13.
9. Для закрытия Мильстрима ввести 20 000 ₽ / 20 / 30, Культуры — 18 000 ₽ / 18 / 26. Проверить накопительные суммы и выгрузку Excel.

Обычная своевременная сдача без ошибок отдельного Telegram-сообщения не создаёт. Уведомления нужны для проблем и ответов продавца.

**«Начать заново»** требует подтверждения: удаляются только сегодняшние учебные отчёты, их версии, вопросы и задания отправки. Планы, сотрудники и доступы сохраняются. Сообщения, уже доставленные в Telegram, остаются. Старые прогоны сохраняются в истории и закрываются для повторной отправки. Новые упражнения автоматически на следующий день не запускаются.

## Перед переходом реальных магазинов

В рабочем сервисе отдельно проверить адреса и назначения сотрудников, планы на дату запуска и реальные графики. Подтвердить графики заранее: штатный контроль начинается со следующего рабочего дня. Передать каждому магазину только его рабочие доступы. Учебные цифры и аккаунты в рабочий сервис не переносить.
