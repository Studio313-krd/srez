# Развёртывание «Среза»

Рабочий сервер: https://srez.studio313.ru/, стэк `srez` (ID 102, окружение 3) в Portainer. Используется `compose.prod.yaml` из ветки `main` репозитория https://github.com/Studio313-krd/srez.git. Один образ для web и worker, PostgreSQL в отдельном томе. Исходные Google-таблицы не изменяются. Яндекс.Диск не требуется.

## Запуск на сервере

1. Настроить DNS и сертификат поддомена в существующем nginx.
2. Скопировать `.env.example` в `.env`, задать домен, уникальный `SECRET_KEY` и пароль PostgreSQL. Сгенерировать ключ: `python -c "import secrets; print(secrets.token_urlsafe(60))"`. На рабочем сервере — `SREZ_DEBUG=false`; шаблонные и короткие ключи не принимаются.
3. Выполнить `docker compose build web`, затем `docker compose up -d`. Старт web/worker зависит от успешной миграции; БД проверяется через `pg_isready`.
4. Создать общего администратора офиса: `docker compose exec web python manage.py createsuperuser`. Пароль вводится интерактивно. Если переносится существующая БД из резервной копии, аккаунт уже будет в ней.
5. Внести proxy location из [nginx.conf.example](nginx.conf.example), подставив домен и сертификат. Проверить `nginx -t`, перезагрузить конфигурацию.
6. Перенести проверенную базу или выполнить импорт пакета по [README](../README.md). Войти по HTTPS, открыть «Управление», сверить магазины, сотрудников, планы и подтвердить графики.

Офис работает под одной учётной записью «Администратор» с полным доступом. Отдельный аккаунт «Видеоконтроль» отключён. Управление доступно по `/management`; вход через общую форму с ограничением попыток. На сервере созданы 83 аккаунта роли `store`, каждый привязан ровно к своему магазину. Демонстрационный продавец отключён. Первичные пароли переданы владельцу отдельным локальным файлом; повтор `issue_store_access` не сбрасывает существующие пароли.

`ALLOWED_HOSTS` — имена без протокола; `CSRF_TRUSTED_ORIGINS` и `PUBLIC_URL` — полный HTTPS-адрес. В рабочем режиме включены Secure/HttpOnly-сессия, CSRF, HTTPS redirect и HSTS для поддомена. Существующий nginx проксирует на `185.72.147.187:9994`; этот порт опубликован согласно конфигурации владельца. Приложение доверяет заголовку HTTPS только от адресов `TRUSTED_PROXY_CIDRS`. Для текущей сети задано `127.0.0.1/32,172.26.0.1/32`: второй адрес — фактически наблюдаемый Docker gateway для запросов nginx. При пересоздании сети проверить адрес заново. Для прямого HTTP-запроса заголовок HTTPS от постороннего адреса игнорируется.

Пример предполагает nginx на хосте. Если nginx в контейнере, подключите web к существующей proxy-сети с уникальным алиасом и укажите upstream по этому алиасу на порт 8000. В контейнере nginx адрес localhost относится к самому nginx; публикация порта приложения наружу не нужна.

## Portainer

Стэк создан способом **Repository**: URL репозитория, `refs/heads/main`, Compose path `compose.prod.yaml`. Portainer получает контекст исходников и собирает образ на сервере. Секреты хранятся в Environment variables стэка. Не заменять эти переменные пустым шаблоном: там находятся ключ приложения, пароль БД и пользовательский токен Telegram.

При обновлении: проверить свежую резервную копию, отправить проверенные изменения в `main`, открыть стэк → **Pull and redeploy**, сохранив переменные окружения. `pull_policy: build` у web обеспечивает сборку; migrate выполняется перед web/worker. Данные остаются в томах `srez_postgres_data` и `srez_backups`. Откат на прежний код допустим при совместимой схеме; иначе требуется согласованное восстановление БД.

## Реестр и правила

Импортировано **83 магазина** из основного кадрового реестра; в Google-отчётах есть 82. Дополнительный магазин и расхождения отмечены в «Управление → Сверка данных». Камерные коды сопоставлены с постоянными кодами реестра. Часы работы в источниках отсутствуют, контроль сроков выключен. Видеоконтроль должен проверить часы, дни и часовой пояс в карточке магазина, затем включить контроль: он начнётся со следующего рабочего дня. Для контроля 15 сентября подтвердить графики 14 сентября. Историческим импортированным отчётам сроки и опоздания не выдумываются.

Срезы 13:00 и 17:00 создаются, если магазин работает в это время; третий — закрытие. Сроки: 13:05 / 17:05 / закрытие + 15 минут. Отправка доступна с наступления среза. При закрытии после полуночи рабочая дата — дата открытия; окно до закрытия + 15 минут относится к ней же. Выходные и заранее введённые исключения учитываются. Поддерживается одна непрерывная смена за рабочую дату.

Сроки созданных ожиданий фиксируются. Изменение графика не переписывает прошлые опоздания; исключения для уже созданного дня поясняются в замечаниях. Будущие праздничные дни задаются заранее. Планировщик восстанавливает пропуски после простоя по сохранённому указателю, партиями до 30 дней на магазин за проход.

Планы меняются добавлением версии в «Управление → Планы»; предыдущие остаются в истории. Импортированные планы помечены «Из таблицы». План чеков необязателен, фактические чеки обязательны. Деление на ноль даёт «—». Администратор заполняет и исправляет отчёты, указывает ФИО продавца и причину исправления; история сохраняет и продавца, и аккаунт, внёсший изменение.

## Telegram и MAX

Реализованы независимые очереди уведомлений в **общий офисный чат каждого мессенджера**. Сообщения содержат новые замечания или ответы продавцов, магазин, дату, срез и ссылку, требующую входа. Подключение описано в [BOTS.md](BOTS.md). Telegram-бот `@srez_notify_bot` создан, токен в Portainer. Группу владелец добавит позже. MAX-бот не создан; оба канала отключены, реальная доставка не проверена.

Одинаковое событие не создаёт повторное задание. Неудачные попытки повторяются с увеличением интервала до часа; учитывается ограничение частоты каждого канала. При таймауте после фактической доставки возможен повтор сообщения. Закрытые замечания и архивные магазины из очереди не отправляются. Историческим пустым строкам не назначаются выдуманные сроки. Состояние подключения, очередь и последняя ошибка доступны в «Управление → Уведомления». Боты предназначены для отправки уведомлений; регулярные сводки и индивидуальные чаты магазинов остаются отдельным этапом.

## Копии и наблюдение

В `compose.prod.yaml` служба **backup** создаёт `pg_dump -Fc` при запуске, затем каждые 24 часа. Копии хранятся отдельно от БД, в томе `srez_backups`; срок хранения — 14 дней. Healthcheck проверяет наличие свежей копии. Это копии на том же сервере: перенос на независимое хранилище пока не настроен.

`python deploy/backup.py` создаёт дополнительную локальную копию в `.local/backups`. На рабочем сервере после импорта и выдачи доступов сохранена свежая копия. Секреты Portainer не входят в pg_dump.

`python deploy/backup.py --restore-check` восстанавливает копию во временную отдельную БД и проверяет чтение пользователей, магазинов и версий. Рабочая БД не перезаписывается. Секреты из `.env` резервируются отдельно.

`docker compose ps` должен показывать healthy у db/web/worker. `/api/health/` проверяет БД. В кабинете офиса появляется сообщение, если проход планировщика не завершался более трёх минут. Логи: `docker compose logs --tail 100 web worker`. Внешний мониторинг поддомена и оповещение о падении сервера настраиваются отдельно.

Для пилота нужны подтверждённые графики и дата начала контроля каждой точки. История двух Google-таблиц и кадровый Excel импортированы полностью. Автосинхронизация с Google не нужна и исключена из плана: после перехода новые отчёты и планы ведутся в сервисе. Автосверка с кассой и управленческие сводки остаются следующими этапами.
